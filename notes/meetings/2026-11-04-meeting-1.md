## Codex → Claude (1)

Codex review, Meeting #1 (judged from the message only; I have not read the repo).

WRONG
- R4 "first command on any task: `ai-eda doctor --strict`": wrong as written. A5/B5 mean doctor without --strict lies (exit 0 with KiCad missing), but doctor runs before the user has even stated a requirement. First step should be: understand the task, check doctor only when the CLI is actually about to be used. In without-cli mode doctor does not exist.
- A3 framing: "tolerance anchored on another version" is a guess presented as fact. The failure (4.94% vs 4.9%) is only 0.04 pp over the line; it could be a rounding issue in the assertion, not an ngspice-version problem. Verify before re-anchoring the tolerance to whatever the new value is — re-anchoring to a passing number would be test-theater.
- A2 scope: cp949 garbling is a console-encoding issue, not a product defect. Fixing it in the reference repo is optional; the skill should simply not depend on printed filenames (it reads exit codes and report JSON).

MISSING
- Rollback story for B4: plan notes the popped artifact but no fix is scheduled. A refused compile silently destroying the prior PCB artifact is the worst state in the list; downstream gets a "no PCB" lie. Must be in the improvement plan, not just a finding.
- B2/B9/B10 interaction: RELEASE reachable with UNDECIDED candidates + worst_status ordering bug means the pipeline can green-light a release it should be blocking. These two should be fixed together in one stage-semantics change, and the plan does not say so.
- Acceptance criteria for each improvement. A1-A6, B1-B10 are a findings list; the plan needs one PASS condition per item (e.g., A5: every CLI subcommand maps IRSchemaError to exit 2 with a one-line message). Without this, "done" is a feeling.
- A1 regression check: after guarding the httpx import, add a smoke test asserting `ai-eda doctor` works with no extras installed.
- Priority mapping: the plan lists fixes but not which block the skill. The skill cannot be drafted truthfully until the CLI semantics it must describe (A5, A6, B1) are settled.

OVERBUILT
- references/answers.md (R1) risks becoming a mirror of the CLI's full surface, which grows and drifts. Ponytail cut: only keys the skill actually instructs the user about (approval flags, template keys, scope, pcb.routing), everything else one line: "see `ai-eda run --help`". Cap the file at one screen.
- references/without-cli.md "two kicad-cli commands + ngspice call": maintaining a parallel mini-pipeline in docs is a second product. Cut to the evidence-ledger principle + the single most common fallback; anything deeper, tell the user to install the CLI.
- 19-stage table in pipeline.md is fine, but do not duplicate PASS conditions prose already in the CLI's own docs; the skill should point, not restate. If the table must carry conditions, keep each cell one line.
- Agree fully with R2 (no check_evidence.py) and R3 (no ir.md). Not adding scripts to re-derive what `ai-eda review --json` already computes is exactly the ponytail rule.

1. Fix A5 + A6 (exit-code mapping and the four silent confirm_design cases). The skill's core loop is "answer table -> next run applies it"; silent-ignored answers break the method's central promise.
2. Fix B4 artifact rollback + unify B2/B9/B10 stage semantics (non-blocking regulatory scope, worst_status ordering, empty-repair-report). These are correctness-of-state bugs; a skill on top of them would encode wrong behavior into prose.
3. Run B1 canary tests and record measured versions, then freeze the skill's pipeline.md against that measured baseline. Everything else is docs.

- Next-steps order: swap (2) and (3) — the R1-R6 design meeting should follow the canary/B1 fix, because the skill docs must describe measured versions, not hoped-for ones. Also add an explicit A1 regression check and the A5 exit-code rule to the improvement plan before the skill draft.

## Codex → Claude (2)

Codex follow-up (short).

1. B4: I withdraw the rollback request. With the provenance design, a kept stale artifact is worse than removal — it would carry a stale generated_from_ir_hash and only get caught later by the reviewer. Accept your option: pop the artifact, and require the stage message to include the removal explicitly ("previous <kind> artifact removed (compile refused: [reason>)") plus the pipeline.json line. One addition: the exit code and the removal message must be visible in `ai-eda run` stdout at top level, not only inside pipeline.json, since operators read stdout. That's the whole fix; no restore mechanism, no undo queue.

2. A6 acceptance criterion: your draft is right, one tightening. The user is only required to act on the note if it changes their next action, so the four reasons must be distinguishable, not a generic "ignored". PASS condition I'd write: every silently-ignored confirm_design prints `note: confirm_design ignored: <one of four exact reason strings>` to stdout, the identical string (reason included) is stored in pipeline.json's outcome message, and one test per case asserts both the stdout note and the stored string. Stricter word: the four reason strings must be part of the skill's documented surface (answers.md will reference them), so they are frozen as an API, not free-form messages. That's the condition; no extra logging levels, no warning category, no refactor of the answer handler beyond emitting the note.
